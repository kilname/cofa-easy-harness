# 비판적 검증 — 믿기 전에 증거 확인

## A. 기준
1. 원본 README/제출 안내의 관련 부분을 다시 읽는다. 실제 담당자 답변이 있는 경우 원문과 적용 범위를 확인한다.
2. `원문 확정 / 담당자 확정 / 추론 / 임시 가정 / 개발 선택 / 미확정`을 구분한다. 정책 숫자, 예외, 우선순위, 제약조건을 코드와 대조한다.
3. 결론에 영향을 주는 판단은 근거 파일·위치를 가리키고, 근거가 없는 가정의 영향과 확인 필요 여부를 명시한다. 요구사항 누락과 허용되지 않은 범위 확대를 찾는다.

## B. 반례
1. 경계 **직전/같음/직후** 및 빈 값, 잘못된 형식, 중복, 0개 결과, 충돌한 조건을 확인한다.
2. 과제에 해당하는 경우 정렬 우선순위·동률·시간 겹침·올림·단위·재계산·저장·보안을 테스트한다. 모든 항목을 무조건 반복하지 않는다.
3. 코드 없이 원본 정책으로 최소 1개의 중요 기대 결과를 계산한다. AI가 만든 코드와 AI가 만든 테스트가 같은 착각을 공유할 수 있음을 의식한다.
4. 정책을 지키면서 결과가 바뀌어야 할 입력 변형(예: 경계 ± 1)을 만들어 유효한 반례를 찾는다.

## C. 실행 증거
1. 적절한 테스트·빌드·CLI·브라우저 검증을 **실제로 실행**한다. 수행 명령, 테스트 수, 실제 결과를 기록한다.
2. 테스트 0개, 전부 skip, 명령 실행 실패, 화면 미확인은 `PASS`로 기록하지 않는다. 기능 검증과 정적 점검을 별개로 보고한다.
3. 실패 시 재현 입력과 원인 가설을 제시해 수정하고, 동일 실패 및 기존 정상 사례를 **재실행**한다.
4. 외부 데이터 전송, 개인 API, 감독 우회, 임의 설치·시스템 변경을 검증 수단으로 사용하지 않는다.

## D. 종료 보고 (짧게)
- 범위/근거: 실제 읽은 파일·담당자 답변
- 검증: 테스트 명령·PASS/FAIL/SKIP/미실행 수치
- 발견 오류: 재현 가능한 사례, 사용자에게 발생하는 영향
- 수정과 재검증: 무엇이 달라졌나
- 미정·미실행: 이유와 제출에 영향이 있나
- 쉬운 설명: 기술 지식이 없어도 이해할 한두 문장

**증명 범위를 넘어서 '완벽', '무오류', '검증 완료'라 단정하지 않는다.**
